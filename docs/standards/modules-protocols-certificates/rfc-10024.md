## What it covers

RFC 10024 defines three hybrid key agreement mechanisms for TLS 1.3 — X25519MLKEM768, SecP256r1MLKEM768 and SecP384r1MLKEM1024 — each combining ML-KEM with an elliptic-curve Diffie-Hellman (ECDHE) exchange. It applies the general hybrid design in RFC 9954 to ML-KEM and assigns the code points that TLS clients and servers use to negotiate these groups. It concerns key establishment only; it does not change how TLS certificates are signed.

RFC 10024 was published by the Internet Engineering Task Force (IETF) in August 2026 as a Proposed Standard on the Standards Track. Like other IETF RFCs, it is a voluntary technical specification: it binds no organization by itself, but it is what interoperable TLS implementations build to, and other authorities' guidance or procurement rules may refer to it.

## Relationship with other standards

[RFC 9954](https://www.rfc-editor.org/info/rfc9954) (Informational, July 2026) provides the framework for combining two key exchanges in TLS 1.3; RFC 10024 instantiates it with ML-KEM from [FIPS 203](/standards/post-quantum/fips-203/). A separate document defining ML-KEM on its own in TLS, [draft-ietf-tls-mlkem](https://datatracker.ietf.org/doc/draft-ietf-tls-mlkem/), is in the RFC Editor queue.

[NIST IR 8547](/standards/transition-and-key-management/nist-ir-8547/) describes TLS 1.3 hybrid key exchange combining ML-KEM with classical algorithms as a practical near-term path and says guidance on it will be reflected in the next revision of [SP 800-52](/standards/modules-protocols-certificates/sp-800-52/). Whether hybrid or ML-KEM alone is preferred varies by authority; see [hybrid approaches](/learn/hybrid/). For implementation choices, see [TLS and web services](/technology-options/tls/).
